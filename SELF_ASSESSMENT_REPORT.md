## What we did not manage

- In [`src/app.js`](src/app.js), `Idempotency-Key` tracking for `POST /api/labs/{labId}/publish` (`usedIdempotencyKeys`) is stored in an in-memory `Set` scoped to the server instance while `labs.published_at` is persisted in SQLite. Because `UPDATE labs SET published_at = datetime('now') WHERE id = ? AND published_at IS NULL` is inherently idempotent in SQLite (`FAQ-12`), repeating a publish call across multiple server instances still returns `200 OK` with the exact same `publishedAt` timestamp and never double-publishes; however, the optional `Idempotent-Replayed: true` response header is only emitted when the retry hits the same process until we move `idempotency_keys` into a persistent SQLite migration in `PA#3`.
- While [`docs/contract/publish.md`](docs/contract/publish.md) and [`test/contract/publish.contract.test.js`](test/contract/publish.contract.test.js) thoroughly cover `POST /api/labs/{labId}/publish` (and `POST /api/submissions/{id}/review` + `GET /api/labs/{labId}/queue` are implemented for the review workflow and Playwright `e2e` test), we have not yet enforced the submission deadline check (`now > lab.deadline_at`, `FAQ-12` condition 1) in the SQLite schema of this slice, as lab creation and deadline scheduling belong to the `PA#3` prototype milestone.

## What we would do differently

- We would add `tsc --noEmit` (`checkJs: true`) and run `npm run e2e` in CI on the very first commit rather than assuming a test that passes in `node:test` will behave identically in a long-running HTTP server process. Running Playwright in CI Run [`42586953474`](https://github.com/danhuupham/leetkob/actions/runs/42586953474) immediately exposed a subtle Node `22.13.0` `node:sqlite` bug (`ERR_INVALID_STATE: statement has been finalized`) caused by V8 garbage-collecting the unrooted `DatabaseSync` instance returned by `open()` in `src/server.js` — a bug that in-process tests in `test/helpers.js` masked because `publishedAt()` happened to hold a reference to `db`.
- When reviewing any existing test suite, we now search for `try`, `catch`, `.skip`, `|| true`, and `continue-on-error` first, and verify that every `4xx` authorization test reads back the database state after the refused call.
